# 05 · 行为与运维：长期怎么用，出事怎么办

> 核心问题：**环境搭好之后，日常使用方式本身会不会成为风险？出问题时有没有预案？**
> 环境决定能不能「进门」，行为决定能不能「长住」。

---

## 1. 使用行为信号

| 信号 | 风险方向 |
| :--- | :--- |
| **使用时段** | 与出口地区当地作息长期严重错位 |
| **使用强度** | 新账号即高强度、长时间、高并发 |
| **自动化特征** | 脚本化请求、异常规律的请求间隔、非官方客户端 |
| **多端 / 多地登录** | 同时从多个地区、多个出口登录同一账号 |
| **环境突变** | 突然换国家、换设备、换浏览器 |
| **内容与用途** | 违反使用政策的内容或用途 |

---

## 2. 方向性原则

1. **作息自洽**：选择与自己真实作息兼容的出口地区，比事后伪装更可靠。
2. **循序渐进**：新账号先正常、适度使用，再逐步提高强度。
3. **固定入口**：日常始终从同一套环境访问；必须变动时，一次只变一个因素，并观察。
4. **多端一致**：网页、桌面、移动端都要满足相同的网络与地区要求。
5. **合规使用**：遵守使用政策。因内容/用途导致的封禁，与环境无关，也最难申诉。
6. **API 与网页分开看**：API 与订阅产品的风控、计费和政策不同，不要混为一谈。

---

## 3. 运维规范

- **上线前检查清单**：每次重大变更（换节点、换设备、升级工具）后，先跑环境体检再访问。
  - 工具：`tools/scripts/verify_environment.sh`
- **变更记录**：环境变更写入 [CHANGELOG.md](../CHANGELOG.md)，出问题时可回溯。
- **定期复测**：出口质量、泄漏测试按周期复查，结果自动归档到 `output/`。
- **重要数据备份**：对话、项目文件定期导出，不把账号当作唯一存储。

---

## 4. 出事后的处理

```
发现异常（验证码激增 / 限流 / 登录异常 / 封禁通知）
        │
        ├─ 立即停止在该环境中进行任何新操作（不要换号继续用同一环境）
        ├─ 记录：时间、最近变更、当时的网络/设备/支付状态
        ├─ 按五层逐项复盘，找出破绽，写入 research/notes/
        ├─ 如认为误封，通过官方渠道申诉，信息保持一致
        └─ 修复环境后再启用新身份，避免沿用任何被关联的节点
```

> 每一次异常都是研究样本：**复盘结论 → 更新原则文档 / playbook / 工具**，形成闭环。
