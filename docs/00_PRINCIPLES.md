# 00 · 风控模型与核心原则

> 本文是整个项目的「世界观」。它不讨论具体节点、具体工具，而是回答：**平台是怎么判断一个账号该不该封的？我们应该朝哪个方向做？**
> 具体方案会过时，这里的原则应当长期成立。

---

## 1. 风控系统的本质：多信号打分 + 关联图谱

不要把封号想象成「某一条规则命中就封」。现代风控（Anthropic 自身 + Cloudflare + 支付方 + 身份提供方）更接近下面的模型：

```
          ┌────────────── 信号采集 ──────────────┐
网络层  →  IP 类型 / ASN 信誉 / 地理位置 / 泄漏
设备层  →  浏览器指纹 / 运行时完整性 / 设备证明
身份层  →  邮箱来源 / 登录方式 / 手机号 / 账号年龄
支付层  →  卡 BIN 国家 / 账单地址 / 支付渠道 / 拒付史
行为层  →  使用时段 / 频率 / 内容 / 多端登录模式
          └──────────────────┬──────────────────┘
                             ▼
              ① 单账号风险评分（是否可疑）
              ② 关联图谱（和哪些已封账号共享特征）
              ③ 政策判定（地区限制 / 使用政策）
                             ▼
              放行 / 验证码 / 限流 / 延迟封禁 / 批量封禁
```

三个关键推论：

1. **没有单点银弹**。插件、节点、邮箱任何一项做到极致，都抵消不了另一层的明显破绽。
2. **关联比单点更致命**。一个账号本身干净，但与已封账号共享设备 / IP / 支付卡 / 邮箱模式，会被连坐。
3. **封禁常常是延迟的、批量的**。「注册成功、能用几天」不代表环境合格——判定可能发生在复核、扣款或批量扫描时。

---

## 2. 我们的目标画像

所有工作的终极目标只有一句话：

> **让账号在所有信号维度上，都像一个「真实、单一、稳定」的、身处服务地区的普通用户。**

- **真实**：信号来源是自然的（住宅网络、原生浏览器、主流邮箱、正常支付渠道），而不是「伪造得很像」。
- **单一**：一个账号对应一套独立环境，不与其他账号/个人日常身份交叉。
- **稳定**：环境长期不剧烈变化（出口、设备、时区、支付方式），变化本身就是信号。

---

## 3. 七条核心原则

| # | 原则 | 含义 | 反例 |
| :-: | :--- | :--- | :--- |
| 1 | **一致性 > 伪装度** | IP 地理、时区、语言、支付地区、使用时段之间要互相自洽 | 美国 IP + 中国时区 + 简体中文 + 国内卡 |
| 2 | **隔离 > 清理** | 用独立环境从源头避免污染，而不是在被污染的环境里擦痕迹 | 在日常 Chrome 里装插件「屏蔽」账号关联 |
| 3 | **少改 > 多改** | 每一处运行时篡改都可能成为新指纹；能用原生手段解决就不要 Hook | 随机化所有指纹，导致环境「独一无二」 |
| 4 | **稳定 > 完美** | 一个长期固定、中等质量的环境，好过频繁切换的「顶级」环境 | 每天换节点、换国家 |
| 5 | **纵深防御** | 每层都假设别的层会失效，关键泄漏点至少两层兜底 | 只依赖插件挡 WebRTC，网络层不处理 |
| 6 | **可验证** | 每个结论都要有可复现的检测方法，不凭感觉 | 「应该没泄漏吧」 |
| 7 | **合规底线** | 内容与用途违反使用政策导致的封禁，任何技术手段都救不了 | 环境完美但大规模自动化滥用 |

## 4. 常见认知误区

- **「装个防指纹插件就够了」** —— 插件只能影响页面 JS 能看到的东西，管不了网络出口、浏览器账号体系、支付和身份。见 [02_BROWSER_ENVIRONMENT.md](./02_BROWSER_ENVIRONMENT.md)。
- **「检测网站全绿 = 安全」** —— 检测站只覆盖一部分公开信号，且有误报（例如把所有 UTC+8 时区一律标红）。它是体检工具，不是平台风控本身。
- **「用美国 IP 最安全」** —— 地区选择应服务于「一致性」，而不是迷信某个国家。
- **「指纹浏览器 = 万能」** —— 商业指纹浏览器本身可能带有可识别特征，且无法解决 IP、身份与支付问题。
- **「被封是因为某一个原因」** —— 通常是多个弱信号叠加越过阈值，复盘时要全层排查。
