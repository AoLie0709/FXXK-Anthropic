# 02 · 设备与浏览器环境：隔离与指纹一致性

> 核心问题：**这个浏览器/设备看起来是不是一个真实、独立、自然的用户环境？**

---

## 1. 两个独立的问题

浏览器层其实有两类完全不同的问题，解法也不同：

| 问题 | 本质 | 主要解法 |
| :--- | :--- | :--- |
| **关联污染** | 环境里残留的身份、Cookie、存储、同步数据、其他插件，把你和别的身份连在一起 | **隔离**（从源头不让它出现） |
| **指纹异常** | 页面能读到的环境特征（时区、语言、WebRTC、Canvas 等）与其他信号矛盾，或带有篡改痕迹 | **对齐**（让特征自然一致） |

把「关联污染」交给插件处理是最常见的方向性错误。

---

## 2. 隔离：层级与取舍

隔离强度从低到高：

```
同一 Profile 里清 Cookie       ← 几乎无效
独立 Chrome Profile（不登录）   ← 最低可接受线，零成本
独立 user-data-dir 启动        ← 文件级隔离，可脚本化
独立浏览器 / 独立系统用户       ← 更强，适合多账号
独立虚拟机 / 独立物理设备       ← 最强，成本最高
```

方向性原则：

- **一个账号一套环境**，不在同一环境里切换多个账号。
- **专用环境只做专用的事**：不登录个人主力账号、国内服务账号，不安装无关插件。
- **浏览器宿主层的东西（账号登录、同步、内置标头），插件管不了**——只能靠隔离避免。

---

## 3. 指纹：对齐而不是随机

- **一致性优先**：时区、语言、地区格式应与出口网络吻合；能通过调整系统/浏览器原生设置实现的，优先原生。
- **篡改即特征**：每一次 JS 运行时 Hook 都可能留下痕迹（函数签名、原型链、行为不一致）。改动面越小越好。
- **不要追求「独一无二」**：过度随机化让你变成罕见指纹；目标是落在「普通用户」的大群体里。
- **硬件特征要可信**：伪造的 GPU / 屏幕 / 平台信息必须与真实系统能力一致，否则比不改更可疑。
- **关注运行时完整性检测**：验证码与反机器人脚本会检测自动化标志、原生函数完整性、环境一致性。

---

## 4. 扩展（插件）的正确定位

| 扩展适合做的 | 扩展做不到 / 不该做的 |
| :--- | :--- |
| 页面可见的时区/语言对齐 | 屏蔽浏览器宿主层账号与同步 |
| WebRTC 策略收紧（配合网络层） | 替代网络层的 IPv6 / DNS 防护 |
| 剥离追踪参数、Referer | 消除其他插件留下的污染 |
| 少量、必要、可验证的运行时修正 | 大面积重写浏览器 API |

本项目自研扩展（Claude Shield）位于 `tools/extension/`，其实现细节见 [ARCHITECTURE.md](../tools/extension/ARCHITECTURE.md)。

---

## 5. 移动端与客户端

- 官方移动 App / 桌面客户端的信号模型与网页不同（设备证明、系统级时区语言、应用商店账号）。
- 移动端需要同样遵守网络层原则（系统级代理/TUN、无旁路）。
- 不同端之间的信号（地区、语言）也要互相一致。

---

## 6. 验证方法

- 指纹检测工具（多个交叉）：关注「不一致」与「篡改痕迹」两类告警，而不是追求全绿。
- 在隔离环境与日常环境之间对比，确认没有共享的 Cookie / 存储 / 登录态。
